Chapter 01 · The agentic shift

Software engineering is becoming a system of delegated work.

The essential change is not that software can write software. It is that AI systems increasingly participate in the choices and actions that move an idea into production.

An engineer may ask an assistant to write a test, explain an unfamiliar subsystem, review a pull request, or troubleshoot an incident. An agent may then inspect code, retrieve context, invoke tools and select intermediate actions. Those capabilities can improve engineering throughput and consistency. They can also move consequential decisions farther from the person who initiated the work.

That distinction matters. Engineering has always delegated tasks—to colleagues, scripts, continuous integration and deployment systems. Agentic AI adds a more adaptive participant: one whose intermediate judgments may be probabilistic, whose inputs may be untrusted, and whose effective actions depend on the tools and credentials available to it.

Leadership's responsibility is therefore not to approve every AI-generated line or recreate every human workflow. It is to design an operating model in which useful autonomy remains bounded by appropriate authority, dependable enforcement and evidence of actual outcomes.

The question is not merely what an agent can do. It is what the engineering system should allow it to decide, execute and change.

The opportunity

Faster feedback, broader analysis, more consistent detection, reduced repetitive work, and opportunities to redesign inefficient delivery practices.

The engineering challenge

Determine which decisions can be delegated, which boundaries remain independent, what happens when an agent is wrong, and how outcomes can be reconstructed.

Chapter 02 · How AI participates in the SDLC

Five shifts in the engineering operating model

Different uses of AI create different engineering consequences. A commenting assistant, a coding agent, and an autonomous release agent should not be evaluated as if they have the same authority.

Five technical shifts

Understand the new operating model

01 · Generation

AI creates code

Productivity may rise while provenance, review capacity, dependency assumptions and secure coding still matter.

Engineering question: Which generated changes must be caught before deployment?
02 · Judgment

AI evaluates changes

Model outputs may vary with prompts, retrieved context, versions and execution settings. An apparent pass is not a deterministic guarantee.

Engineering question: How are consequential misses measured?
03 · Execution

Agents use tools

Risk moves from advice into real actions: GitHub reviews, configuration updates, merges and deployment calls.

Engineering question: Which actions can the identity perform without a human?
04 · Authority

AI can influence decisions

Recommendation, delegated execution and autonomous authorization are materially different trust models.

Engineering question: What independently prevents excess authority?
05 · Operations

Behavior evolves

Changes to model, prompt, tools, retrieval or workflow can shift outcomes without a conventional code change.

Engineering question: What is versioned, evaluated and monitored?
Important distinction

Not all risks are new

Access misuse, defective code and missing logs already existed. AI may change their mechanism, likelihood, scale or observability.

Engineering question: Can existing tools address the problem?
What to retain

AI involvement is not a single risk category. The relevant engineering questions change with the SDLC activity, tool permissions, decision authority and production consequences.

Chapter 03 · Understanding delegated authority

Who decides—and who actually acts?

AI-assisted review, agent-executed human approval, and autonomous AI approval are different operating models. The boundaries between them are not established by a GitHub approval icon alone.

Worked architecture · Example 01

Can an agent submit an approval the engineer has already decided to give?

An engineer reviews a stacked set of pull requests with an AI assistant. The engineer decides to approve three changes and instructs the agent to submit the approvals through GitHub tools.

What this design offers: Less repetitive interaction and a smoother workflow for experienced reviewers.

Where it can fail: The agent may act on a different pull request, a changed revision, or an instruction it inferred rather than received. A human-linked credential does not alone prove the human authorized that precise action.

Engineering question

Could the agent approve PR B, or a new commit of PR A, using credentials and instructions intended only for the reviewed revision of PR A?

Investigate delegated approval (R01) · Investigate revision validity (R04)

Three scenarios, three different assurance questions

AI advisory review

A model comments on a pull request; a human still authorizes changes.

Failure: Incorrect guidance, over-reliance, context leakage and unobserved quality deterioration.

Design: Keep GitHub approval authority with people; evaluate useful findings and severe misses.

Challenge: Seed representative known defects, measure accepted findings and false negatives, test outbound context.

See Engineering + IA investigation →
Agent-executed human approval

An engineer decides; an agent uses GitHub tools to execute that decision.

Failure: Execution authority may exceed a one-PR, one-revision human instruction.

Design: Bind intent to PR/SHA; restrict tools, identities and revocation; independently enforce scope.

Challenge: Attempt approval of another PR or amended SHA using the same agent access.

See Engineering + IA investigation →
Autonomous AI approval

A model's risk judgment may influence approval authority or eligibility.

Failure: False-low-risk classification becomes an authorization error; privileged identities may bypass review.

Design: Deterministic exclusions and independent authorization gate; fail to human; monitor drift and escapes.

Challenge: Have a prohibited shared dependency classified low-risk; confirm GitHub/eligibility gate still blocks.

Chapter 04 · Understanding failure mechanisms

Not every risk is new—but the pathways can change.

AI may amplify familiar problems such as unsafe code, overprivileged credentials and weak release discipline. It also introduces new failure modes where lower-trust text influences tool-using systems or probabilistic decisions acquire operational authority.

Common misconception

Two model assessments that agree are not automatically an independent authorization mechanism. Agreement can improve analysis, but a trusted policy gate must still decide whether the resulting action is permitted.

Chapter 05 · Designing better engineering systems

Better engineering, not simply more safeguards.

The design challenge is to combine useful AI judgment with appropriate constraints—while reconsidering whether old workflows are still the right ones to preserve.

AuthorityWhat decision or action was delegated? Who remains accountable?
EnforcementWhich independently applied permissions, identities and gates restrict behavior?
EvidenceCan engineers reconstruct the instruction, revision, action and result?

Nondeterminism does not mean uncontrolled authorization

Probabilistic judgment

An AI reviewer assesses the diff and may label it low-risk. Test behavior using labeled cases, repeated runs, critical miss analysis and configuration tracking.

Deterministic constraint

A trusted policy gate rejects excluded files or missing requirements regardless of the AI verdict. Challenge this boundary with deliberate bypass attempts.

Design principle: Let models provide judgment where useful; use independently enforced rules to bound what that judgment can authorize. Two agreeing models are not an independent hard gate.
Design alternatives

Start with the engineering objective—not the existing approval ritual.

When reviews are slow, AI auto-approval is one option, not the inevitable destination. Other options include simplifying reviewer routing, retaining human authorization while automating execution, improving deterministic eligibility rules, or removing reviews that do not actually improve change quality.

Compare those alternatives by review effectiveness, developer experience, implementation complexity, bypass resistance, maintenance burden, and recoverability—not just by how quickly a PR merges.

External guidance informs the method. It doesn't validate the architecture.

This educational Field Guide is an independent synthesis of secure development practices, AI security research, internal-control principles and platform-specific documentation.

Technical platform documentation can establish that a feature exists. It cannot show that a particular engineering organization has configured or operated that feature correctly. Similarly, standards inform our questions without prescribing one universally correct agent architecture.
