ASSURANCE / A PRACTITIONER DESIGN CHALLENGE

How do we gain assurance over AI-enabled software development?

AI can help develop, review, authorize or execute a software change. Each role changes what needs to be evaluated. This field guide uses one illustrative AI-assisted approval architecture to connect engineering safeguards, compliance obligations and broader technology risk—and invites practitioners to challenge the approach.

Working model, not a prescription. The safeguards and tests below are proposed examples, not claims of implemented controls, verified vendor assurances, SOX compliance or external-auditor reliance.

01 / UNDERSTAND THE USE CASE

What is AI allowed to do?

The assurance approach depends on whether AI is a developer, reviewer, approver or autonomous operator. A human-authored change with AI review is different from AI-developed code reviewed by another AI. Greater autonomy and common dependencies require greater scrutiny.

Human developer

Creates a pull request in a company-managed source repository.

Deterministic eligibility

Company-governed scope and mandatory policy rules precede AI assessment.

Two AI reviewers

One vendor-operated reviewer and one reviewer using company-owned logic with cloud-hosted services. Qualifying agreement is required under the proposed design; agreement does not establish correctness.

AI sign-off and human merge

AI review may satisfy a selected approval path; a human performs the merge. Whether that human supplies independent judgment is a separate question.

Non-AI release controls

Existing post-merge checks govern deployment; production monitoring traces running changes to deployment jobs, Artifactory artifacts, source revisions and originating PRs.

Shared responsibility: Identify who controls the hosted model, review code, runtime, tools, permissions, input data, policy and incident response. Review relevant vendor assurance reports and customer responsibilities rather than assuming either company controls the whole agent.

02 / ESTABLISH THE FOUNDATIONS

What must already be working?

Validate the traditional SDLC controls and the AI trust foundations before treating reviewer results as approval evidence. A second AI model does not repair ineffective GitHub enforcement or unreliable classification data.

Protected repositories

Global branch rules, required checks, CODEOWNERS, privileged bypass routes and direct-to-production paths.

Independent authorization

Humans, bots and service accounts cannot authorize excluded changes or modify their own approval rules.

Policy and administrator independence

Segregate application repositories from bot logic, policy, workflow and credential administration; govern changes and access reviews.

Approved testing baseline

Required CI, security, financial-impact and business-critical tests are defined and enforceable.

Security and vendor boundaries

Document shared responsibility, evaluate applicable SOC reports and restrict untrusted PR input and agent permissions.

Trusted classification inputs

Validate dependency maps, labels and tagging, ownership, provenance and who can edit model context; preserve independent populations.

03 / VALIDATE BEFORE GO-LIVE

How would we establish initial confidence?

Apply practical program controls: approved requirements and configuration baselines, security review, QA, adversarial and false-data injection, independent human adjudication, parallel testing, documented acceptance criteria, management sign-off and a safe suspension route. Reviewers must also be evaluated for correlated false-low-risk outcomes, not just matching scores.

What would we test?

These six evaluation objectives are examples for this architecture; each test needs source evidence and an expected result.

Assurance objectiveEvidence needed to assess it
Change eligibilityValidate repository exclusions, ownership and downstream dependency maps. Inject a hidden billing dependency and a missing map; verify mandatory human routing.
AI reliabilityIndependently adjudicate real and adversarial PR cases; measure consequential false-low-risk classifications and test two-model correlated misses.
AuthorizationInspect effective GitHub rulesets, bot privileges and CODEOWNER routes; test absent/skipped/stale AI outcomes and privileged bypass attempts.
Policy integrityTrace approved model, prompt, mapping and rule changes; attempt self-relaxing policy edits; verify current revision and policy version binding.
Deployment integrityReperform failed/skipped CI gates, source-to-artifact checks, and approval-to-production version/digest tracing.
Continuous monitoringReconcile complete independent merge/deploy populations to recorded approvals; test missing events, alerts, escalation and suspension.

Security is not a seventh isolated checklist: evaluate prompt injection, least privilege, secret handling and enforcement independence within the relevant authorization, testing and monitoring procedures.

04 / OPERATE AND MONITOR

What should management continuously know?

Engineering and Security own operational safeguards and response. Risk and GRC should be able to challenge exceptions; Internal Audit should have access to inspect the underlying evidence without becoming the control operator.

Configuration and authority drift. Detect changes to GitHub rules, CODEOWNERS, bot permissions, models, prompts, policies, dependencies and labels; validate approved changes and trigger re-testing.

Behavior and negative tests. Monitor reviewer disagreement, periodic injected false-risk cases, adjudicated misclassifications, skipped evaluations, incomplete runs and unexpected passes.

Release and incident traceability. Reconcile production versions through deployment job, artifact identity, source SHA and PR; tie incidents to originating changes and feed approved improvements back into tests and eligibility rules.

Alert reliability. Verify event completeness, data freshness, alert delivery, escalation, suspension and remediation. An empty dashboard does not prove absence of exceptions.

Exploratory idea: An independent AI assurance challenger might continuously compare expected controls with observed settings, test results and alerts. Its independence, feasibility and cost remain open for discussion; it would not certify controls or change approval policy.

05 / INDEPENDENTLY EVALUATE THE EVIDENCE

What can an auditor reasonably conclude?

Continuous management monitoring can make evidence available throughout the period, but second- and third-line challenge and external-audit testing still require reliable source populations, effective configuration history, independent reperformance and assessment of exceptions. Point-in-time observations cannot automatically establish period-wide operation.

Design

Are scope, authority, safeguards, ownership and failure responses appropriately specified?

Implementation

Are effective rules, permissions, checks and negative tests demonstrably configured?

Operation over time

Do complete, reliable records support consistent execution, exceptions, model changes and intervention across the relevant period?

Different objectives: Compliance assurance tests applicable requirements and reliance criteria; broader risk evaluation also considers model behavior, vendor dependencies, security and operational resilience. Neither is established by two AI reviewers agreeing.
