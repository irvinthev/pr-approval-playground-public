THE PROPOSAL

Agent-executed human PR approvals

Human decides · Agent submits

An engineer reviews three stacked GitHub pull requests and explicitly decides to approve each. An agent submits the reviews through GitHub tools to reduce repetitive work. One PR is rebased after the engineer's decision. The agent's credentials are broader than the intended action, and instruction-to-action traceability has not been demonstrated.

Engineering objectiveReduce review-submission friction
Central tensionExecution speed vs. authorization fidelity
Assessment basisFictional scenario + engineering judgment
RECOMMENDED DIRECTION

Conditionally pursue.

Narrow the design

Explore a constrained approval executor rather than giving a general coding agent broadly reusable approval authority. Preserve the human decision while making revision scope and execution boundaries explicit.

What the challenge changed

From “Can an agent click Approve?” to “Can it execute only the exact approval the engineer authorized?”

    Realistic failure sequence

    The engineer approves revision A. A later rebase produces revision B. An agent with broad credentials submits approval without confirming fresh authorization for B. GitHub records the action, but that record alone doesn't establish the engineer's judgment on B.

    Strongest counterargument

    Existing GitHub branch rules may already invalidate stale reviews or block a merge after a push. If those rules are consistently enforced, a simpler execution workflow may be sufficient.

    Alternative worth testing

    Investigate whether a small batch submitter—or improved native GitHub routing—solves the actual friction with lower operational complexity than a general agent.
